## 1. 必须遵守的开发循环

具体四期操作、通过门槛、指标冻结和记录模板以 [验收标准](ACCEPTANCE.md) 为准。现有方案分别用X15验证GitHub原生/重建链、X16验证huanyuzhilian实际运行与同条件收益；不能把此前静态分析或核对旧报告当成本次新测试通过。

1. 先定义本流程的输入、预期结果、失败行为、测试素材和通过阈值，再开发实现。
2. 在本机运行新源码，通过真实文件、模型、设备或界面完成当前流程；检查实际产物和副作用。
3. 验证正常输入、关键边界、失败恢复与停止清理；回归本次变更影响的已通过流程。
4. 记录命令、版本、退出码、实际结果、日志/样片/截图及剩余问题。自动化能验证的行为由脚本断言；画质、听感和真实界面记录人工检查结果，不冒充自动判定。
5. 当前阶段的必需用例通过且证据完整，即可继续下一流程。一期开发阶段先完成基本功能验证和完整主流程短测，长时、批量和跨环境用例列入首版后的集中验收。

缺资源或账号时，将受影响用例记为条件缺失，并继续具备条件且无依赖的任务。已通过流程在代码、模型、驱动或配置发生相关变化后需要重新验证。修复局部问题时先跑针对性检查，再跑受影响回归，避免无变化重复全量压测。

流程放行结果使用“待验证/通过/失败/条件缺失”记录，与 FUNCTION_MATRIX.md 的六种功能状态分别管理。本机单流程通过不能把一个包含多分支的原功能整体标为端到端通过；真实 GPU/驱动/平台能力必须有对应环境证据。Mock 仅用于逻辑回归，不作为真实功能放行依据。
