# V05-04b-05 回调平滑候选：不设为默认

决策：候选使发送间隔更平稳，但实际接收连续性变差；不采用为默认，不继续相同配置短测刷结果。保留实验开关及失败证据，原回调调度仍为默认。V05-T1与虚拟摄像头连续性待办不删除。

## 方案和有限验证

`AudioVideoClock` 按累计帧/采样预测视频时刻，初始8帧保留设备预缓冲；最近64次音频回调相位中位数校正，每帧最多调整0.1ms，偏差超过80ms明确失败。内存有界，既不改变帧编号，也不补帧、丢帧或伪造设备成功。

原真实回调记录的软件回放，目标视频间隔由16.426～64.601ms缩至39.9～40.1ms；此回放只验证算法，不是设备效果。3项测试验证回调突发、缓慢设备漂移跟踪和乱序/失锁失败。回调契约测试确认默认模式不调用候选时钟。

## 上游协议核对与限制

核对与本机pyvirtualcam版本相符的[v0.12.1发送实现](https://github.com/letmaik/pyvirtualcam/blob/v0.12.1/pyvirtualcam/native_windows_obs/virtual_output.h)及[共享内存队列源码](https://github.com/letmaik/pyvirtualcam/blob/v0.12.1/pyvirtualcam/native_windows_obs/queue/shared-memory-queue.c)：发送端写入三槽共享区并更新最新索引，不等待逐帧消费确认；同一上游文件保留的禁用读实现也直接读取最新索引。

这是发送协议证据，不证明本机自定义C920接收DLL与上游接收实现逐行相同。结合实际重复/缺帧，可推断消费相位和采样抖动值得进一步定位；尚不能将原因全部归结为模型或驱动缺陷。原协议零重复/缺帧门槛保持，平台接收端和30分钟验收仍缺证据。

## 后续安排

- 虚拟摄像头连续性作为明确技术阻碍保留，后续需要接收端/驱动有依据的验证或带原始PTS的输出通路对照，不无限调整同一路发送节奏。
- 继续同属V05的独立产品接入：控制台输出配置、场次启停、运行状态和失败诊断；不得把界面接入算作V05放行，也不进入正式发布。
- 实验性平滑默认关闭，普通产品流程不暴露算法参数；必要原功能和最终功能范围保持不变。
