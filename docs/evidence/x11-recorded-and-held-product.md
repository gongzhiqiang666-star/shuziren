# X11 录播互动 / 手持商品候选

日期：2026-11-14。X11-01 完成；X11-02 录播音轨原型完成；X11-03 录播产品接入通过；手持商品条件缺失。

## 两个独立子对象

录播互动不是普通数字人实时回复。其输入是已有视频/流及原音轨：ASR 只产生带来源身份的候选时间段，经规则/人工批准后，在固定区间将原音轨置静音并覆盖回复音频；视频时间轴不得移动。直播弹幕回复仍由现有实时链负责，不能重复播同一回复。

手持商品是人物与真实商品外观共同生成或绑定的画面。现有 BiRefNet 抠图、弹窗商品图和 KT 板透视覆盖只证明商品贴图能力，不等于人物真正拿着商品；不得把 KT 证据计入手持生成通过。

## 录播原型

新增 `scripts/recorded_interaction.py`：每个替换区间要求整数毫秒、严格有序无重叠、不越媒体边界、唯一来源 ID 和本地普通回复音频；回复长于批准区间时拒绝，不通过加速或截尾掩盖。混音保持原音轨总时长，批准区间先静音再覆盖回复，区间外音频字节不变。

5 项测试覆盖两个真实 WAV 回复、多区间时长/外部音频保持、重叠/倒序/越界/重复/未知字段、缺文件/链接、回复超时、空计划及真实 MP4 封装。真实 FFmpeg 生成 320×240、25fps、H.264/AAC 源，事务层抽取原音轨、替换两个批准区间、复制视频流并以 AAC 原子发布；输出保留源的 38 帧、媒体时长及音视频双流。无效计划不会覆盖旧成片；FFmpeg 启动后取消会定向终止本任务进程，旧成片字节不变，pending 与任务临时目录均清理。

真实内容链已在 `logs/validation/x11-recorded-real-indextts-02/result.json` 通过：IndexTTS/CUDA 生成 7.59 秒源语音与 1.54 秒回复，模型只加载一次；FunASR 从源 MP4 得到 50～7445 ms 区间和正确原文，替换后的 H.264/AAC MP4 为 320×240、189 帧、7.595 秒，二次 FunASR 正确识别“好的，已经为您记录。”。授权门禁版在 `x11-recorded-real-indextts-03` 再次真实通过，并明确输出 `reference_authorization=unknown`、`production_eligible=false` 和发布阻断原因。

ZipVoice 首次使用一期最小运行根时因缺 Vocos 声码器真实失败，记录在 `x11-recorded-real-01`；增加显式模型根后，`x11-recorded-real-zipvoice-02` 以独立 `zipvoice_distill`/`vocos-mel-24khz` 真实通过：CUDA 生成 6.73 秒源语音与 1.80 秒回复，模型只加载一次，最终 H.264/AAC MP4 为 168 帧、6.741 秒，二次 FunASR 识别“好的，已经为您记录啊。”。这证明默认包资源门禁应拒绝缺 Vocos 的配置，而完整外置模型根可用；其参考音授权仍为 `unknown`，发布资格为 false。发布必须换成授权状态明确且听审通过的音色。LLM 生成回复、实时直播互动和人工质量仍不在本项结论内。

`x11-recorded-real-omnivoice-01` 使用同一协议完成 OmniVoice/CUDA 实测：源语音 6.72 秒、回复 2.08 秒，模型只加载一次；源文和 250～6565 ms 区间识别正确，最终 H.264/AAC MP4 为 168 帧、6.741 秒，二次 FunASR 识别“好的，已经为您记录。”。因此录播技术子对象已在 IndexTTS、ZipVoice、OmniVoice 三个本地引擎上通过相同真实链。三者使用的历史参考音授权状态均为 `unknown`，不改变发布阻断。

## X11-03 手持动作视频任务接入

LTX 动作视频不再只停留在提供者适配器。新增受管任务核心：请求前冻结手持商品图、音频、提示词、分辨率、帧率、实例类型和输入摘要；素材复制到任务独占目录，RunningHub Key 只传入活动线程且不写 `task.json`；同一时刻拒绝第二任务，支持取消、重启中断清理、失败清理、成功结果受管路径和 SHA-256 复核。提供者返回其他路径、空文件或产物被篡改时均拒绝读取。

任务的预演、启动、状态、取消和 MP4 读取已接入本地 HTTP 服务；字段类型和完整集合在进入任务层前校验，服务退出会取消并等待活动任务。页面已补齐手持图→讲解音频→LTX 的预演、启动、状态轮询、取消、预览与下载控件。本机 Chrome 以新建图片和 1 秒 24 kHz WAV 走通两级预演：Qwen 工作流 `2113900488247824386` 和 LTX 工作流 `2031016553440878594` 均显示正确，动作计划为 720p、25 fps、plus 实例，图片/音频摘要均为 64 位；两个 Key 输入框保持为空。报告和截图位于 `logs/validation/x11-hold-motion-ui-plan-01`。

任务输入额外拒绝符号链接；预演后复制到受管目录时重新计算图片与音频摘要，任一源在预演到复制之间变化都会在任务记录发布和云调用前失败并清理目录。控制台把已配置运行根中的 FFprobe 显式交给任务，缺少探针时在云调用前拒绝；云结果必须经 FFprobe 解析出视频流、正尺寸和正时长才可发布。真实 FFmpeg 生成的 96×128、H.264、0.4 秒样片通过，文本伪装的 MP4 被拒绝。

轮询得到成功状态后会在下载前和下载后再次检查取消；下载过程中取消时，迟到 MP4 立即删除且不会转为成功。任务核心与 LTX 适配器 9/9、控制台 HTTP 全量 63 项通过（1 项需显式真实 FFmpeg 条件而跳过），新增页面脚本语法通过。本轮未使用真实 Key 触发付费生成；因此放行源码任务生命周期、服务协议、媒体门禁和无密钥页面预演，真实动作质量、费用、服务端取消及成片页面播放继续等待授权条件。

动作预演、启动和取消沿用控制台管理员边界，不加入运营角色白名单。角色专项以 viewer/operator/admin 三个独立店铺实例验证：viewer 和 operator 的预演、带 Key 启动均在任务管理器创建前返回 403，管理员同字段继续进入素材校验；拒绝事件按账号、店铺、角色和路径进入授权审计。媒体读取仍沿用现有本机回环、受管任务 ID 和摘要复核模型，不新增公网入口。
