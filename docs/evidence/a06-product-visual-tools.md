# A06-04 商品抠图与 KT 覆盖验证

## 透明产物与模型兼容

2026-11-14 使用本机发行运行时中的 BiRefNet、GroundingDINO 和 RTX 3060 运行真实推理。首轮暴露两个随包兼容问题：FP16 权重接收 FP32 输入，以及当前 Transformers 将 `box_threshold` 参数改名为 `threshold`。实现现按模型参数 dtype 转换浮点输入、保持 token 整数类型，并兼容两代后处理签名；复测模型加载与推理成功。

新增 `cutout_bgra` 透明输出，同时保留原 `cutout_bgr` 白底接口。主体连通域用于限制范围，边缘继续采用 BiRefNet 概率，不再全部二值化为硬边。真实 480×854 授权画面输出 768×768×4 PNG，503790 个全透明像素、10876 个半透明像素，完整写入并解码。该画面是模型链路验证素材而非商品质量语料，因此只证明真模型兼容、四通道产物及软边存在，不宣称商品抠图主观质量已验收。

## KT Alpha 合成

本地和远程 PNG 均以 unchanged 模式读取，三通道保持原行为，四通道在透视变换后使用软 Alpha 与直播帧混合。受控测试覆盖透明背景不覆盖原画面、半透明像素混合、商品长宽比 contain、非法通道拒绝及本地 PNG Alpha 保留。专项 3 项及完整恢复基线通过。

后续子项仍需完成 KT 生命周期（随形象启动、商品轮播切换、停播释放）、真实带 KT 板视频和商品图直播回采，以及保存重开链路。

## 动态虚拟设备回采条件

本机补做动态设备短测：产品覆盖器按 175 个逐帧移动四边形合成带 Alpha 的绿色商品，`pyvirtualcam` 成功写入 `OBS Virtual Camera`。DirectShow 枚举显示当前可读的 `Tblive Virtual Camera` 只支持 1280×720、30 fps；按该唯一格式回采得到 165 帧 FFV1 并可完整解码，但所有帧均为约 `[126,129,127]` 的静态灰画面，绿色商品为 0 帧。由此确认输出与输入是两套不同虚拟设备，不能用此结果冒充设备闭环。

结构化失败证据、接收日志、完整回采和抽帧位于 `logs/validation/a06-kt-device-capture-03`。恢复条件是安装/暴露与 OBS 输出匹配的 DirectShow 接收端，或增加能写入 Tblive 的受支持输出后端；在此之前保留 KT 进程内动态合成和生命周期通过结论，设备回采继续待验。

## KT 直播生命周期与重开

数字人直播启用 KT 跟随后会先关闭旧状态、解析当前形象目录、加载并校验板卡缓存；缓存无命中时明确拒绝开播。首件商品在启用前载入，每段话术保留所属商品身份，轮播到下一商品时先切换贴图再合成语音；相同商品不重复读取本地文件或网络。启动失败和正常停播均回收全局覆盖器。

板卡缓存改为同目录暂存、fsync、原子替换，并严格验证 `boxes/valid/frame_size/hit` 的形状和值。受控重开测试从磁盘两次载入同一缓存和透明 PNG，均通过真实 `frame_player_kt.StreamPlayer` 提交帧，重开前后输出逐像素一致。标准 480×640 KT 模板真实检测出四角 `[33,19] [447,19] [447,621] [33,621]`，透明商品透视覆盖改变 63656 个像素。生命周期专项 6 项、商品工具累计 33 项和完整恢复基线通过。

恢复基线同时拦截并修正两处接口兼容回退：`process_face_frames` 必须继续返回 `None`，`save_frame_data` 必须保持原五参数签名。人脸统计现从位置文件读取，不改变原公开接口。验证脚本也修复了 PowerShell 将 unittest 的正常 stderr 进度误当终止错误的问题。

实际摄像头/虚拟摄像头的动态板卡回采、真实商品图主观边缘和长稳仍列入首版集中验收，不阻塞 A06-05。
